# MCP Server and Tool Definitions

## Where the code lives, and why it is not in this directory

The executable server is [`../app/mcp_server.py`](../app/mcp_server.py) and the
client adapter is [`../app/mcp_client.py`](../app/mcp_client.py).

Python modules are deliberately **not** placed in this directory. The official
SDK is imported as `mcp` (`from mcp.server.fastmcp import FastMCP`), and the
repository root is on `sys.path`. Adding an `__init__.py` here would turn
`./mcp/` into a regular package that shadows the installed SDK, and every import
of the real `mcp` would resolve to this folder instead. This directory therefore
documents the MCP layer; the code it describes lives under `app/`.

## Running the server

As a standalone MCP process over stdio:

```bash
python -m app.mcp_server
```

Verified end to end in CI by [`../scripts/mcp_check.py`](../scripts/mcp_check.py),
which launches that command as a subprocess, completes the MCP handshake, lists
the tools, and calls two of them. That is the check which proves the server is a
genuine MCP server rather than a set of functions with an MCP-shaped wrapper.

In the deployed single service, `app/mcp_client.py` launches this server as a
local subprocess and uses the MCP stdio protocol for `initialize`, `list_tools`,
and `call_tool`. The server and web app remain in one free-tier service, but the
agent never bypasses MCP by calling the backing Python functions directly.

**The subprocess is started once, at application startup, and the session is
shared by every request.** Spawning per call measured at roughly 590 ms and
51 MB, which on a small container means the health probe forks an interpreter on
every check and a burst of concurrent traffic can exhaust memory. With one
session, `/health` costs about 3 ms and 20 concurrent tool calls complete in
23 ms against a single 51 MB child.

The session is owned by a dedicated supervisor task. `stdio_client` and
`ClientSession` are anyio context managers whose cancel scopes must be exited on
the task that entered them, so they cannot be held open in a shared exit stack
and closed from a request handler — doing so raises *"Attempted to exit cancel
scope in a different task"*. If the child process dies, the next call
transparently restarts it; `tests/test_mcp.py` covers both the shared-session and
restart behaviours.

## Tool definitions

Six tools. Two read the RAG index, four read or draft against synthetic records.
Schemas are generated by FastMCP from the type hints on each function, and are
served live at `GET /tools`.

| Tool | Arguments | Returns | Backed by |
| --- | --- | --- | --- |
| `search_policy_documents` | `query: str`, `limit: int = 4` | Ranked policy chunks with `id`, `document`, `section`, `text`, `score`, `support` | RAG index |
| `get_policy_section` | `document: str`, `section: str` | Every chunk of one named section | RAG index |
| `lookup_employee_profile` | `employee_id: str` | Employment type, role, manager, home state, office | `mock_data/employees.json` |
| `check_pto_balance` | `employee_id: str` | `available_hours`, accrual rate | `mock_data/pto_balances.json` |
| `lookup_benefits_status` | `employee_id: str` | Enrolment status and elected plans | `mock_data/benefits.json` |
| `create_mock_hr_ticket` | `employee_id: str`, `summary: str`, `category: str`, `confirmed: bool = false` | Confirmed mock draft with `confirmation_obtained: true`, `mock_only: true` | Returns a draft only; writes no real system |

## How the agent discovers and calls tools

1. `app/mcp_client.discover_tools()` calls `list_tools()` and returns each tool's
   name, description, and JSON Schema.
2. `app/planner._to_anthropic_tools()` maps those schemas onto the Messages API
   `tools` shape. Nothing is hard-coded — a tool added to `mcp_server.py` becomes
   available to the model with no change to the planner.
3. The model returns a `tool_use` block. The planner passes the name and
   arguments to `app/mcp_client.call()`, which invokes `call_tool()`.
4. The result is appended as a `tool_result` and the loop continues until the
   model stops requesting tools or the iteration bound is reached.

The orchestrator never imports `app.rag` or `app.data`. Its only route to policy
text or employee records is `call(name, arguments)`.

## Error and safety behaviour

- A missing record returns a structured `{"error": ...}` payload rather than
  raising, so the planner can degrade to a policy-only answer.
- `create_mock_hr_ticket` is refused both by `app/planner.py` and at the MCP
  tool boundary unless the request carries explicit `confirmed: true` after
  user confirmation. This is enforced in code, not by prompt, so the model
  cannot talk its way past it. A direct MCP caller receives
  `confirmation_required` if it skips the flag.
- An exception from any tool is caught, recorded in the trace, and returned to
  the model as an error result; a failing tool does not fail the request.
